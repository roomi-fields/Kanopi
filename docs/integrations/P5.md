# Kanopi × p5.js — Phase 0 audit

Audit du gap entre l'UX p5.js native (p5 Web Editor + `p5.js` lib) et
l'intégration actuelle Kanopi (nulle), suivant la procédure
`feedback_language_integration_procedure` et la structure en 6 zones
d'`ADAPTER_SPEC.md §2`.

Date : 2026-04-23. Adapter actuel : **aucun** — `runtimeFromExt` dans
`packages/ui/src/lib/workspace/types.ts` ne reconnaît pas `.p5` / `.p5js`.

---

## Contexte : p5.js n'est pas un langage

p5.js est **une bibliothèque JavaScript** pour le creative coding,
inspirée de Processing (Java, MIT Media Lab). L'utilisateur écrit du
JS standard avec des globals injectés par p5 : `setup()`, `draw()`,
`ellipse()`, `background()`, etc.

Conséquences pour Kanopi :

- L'éditeur réutilise `@codemirror/lang-javascript` (déjà en place
  pour Hydra) — **aucune extension CM6 nouvelle**.
- La zone B (native editor UX) se limite aux extras p5 : autocomplete
  de la liste des globals p5, tooltips signatures. Cas ADAPTER_SPEC
  §B cas (b) si pas de module CM6 upstream dédié.

## Audit par zone

### A. Runtime engine — 🟢 simple

| Feature                     | p5.js natif                         | Kanopi projeté             |
| --------------------------- | ----------------------------------- | -------------------------- |
| Instanciation               | `new p5(sketch, container)`         | Instance mode (cf §A.1)    |
| Eval du code                | Sketch = closure avec setup()/draw()| `new Function('p', code)(pInstance)` |
| Canvas                      | `createCanvas(w, h)` dans setup     | Canvas dédié comme Hydra   |
| Re-eval / hot swap          | `p.remove()` + new sketch           | ✅ clean lifecycle          |
| Audio (`p5.sound`)          | Extension optionnelle               | 🟡 v2, AudioContext partagé Strudel |
| WebGL mode                  | `createCanvas(w, h, WEBGL)`         | ✅ same canvas              |

#### A.1 · Instance mode vs global mode (décision)

**p5.js a deux modes** :

- **Global mode** : `window.setup = () => {...}; window.draw = () => {...}; new p5();` — canonical dans tous les tutoriels, mais **pollue globalThis** avec ~300 fonctions (ellipse, rect, noise, random, color, sin, cos, dist, map, …).
- **Instance mode** : `new p5((p) => { p.setup = () => {...}; p.ellipse(50, 50); })` — clean, préfixe obligatoire mais nécessaire pour composer avec d'autres runtimes.

**Décision recommandée : instance mode**, pour éviter les collisions
avec Strudel/Hydra. Précédent : la collision `speed` Strudel↔Hydra
(cf `project_hydra_adapter_quirks`) a coûté plusieurs heures de debug.
p5 ajouterait des collisions similaires sur `noise`, `random`, `color`,
`map` — tous présents dans Hydra, Strudel ou les globals DOM.

**Trade-off** : l'user doit écrire `p.ellipse(50, 50, 20)` au lieu de
`ellipse(50, 50, 20)`. Pas identique au p5 Web Editor. À documenter
clairement dans le snippet starter.

Alternative : **global mode + sandbox de cleanup** — re-écrire globalThis.noise etc. au start/end de chaque eval. Plus fragile, plus complexe. Non retenu.

| Feature                     | p5 Web Editor                       | Kanopi                     |

**Gap B** : cas (b) d'`ADAPTER_SPEC`. Pas de module CM6 dédié
upstream → autocomplete/tooltips vont au backlog `PROGRESS.md §5.4`,
idem Hydra. L'user a du highlight JS générique, suffisant pour v1
parité Flok (qui utilise aussi JS générique pour p5).

### C. Event surface — 🟡 minimal

| Event type        | p5.js natif                          | Kanopi projeté             |
| ----------------- | ------------------------------------ | -------------------------- |
| `trigger` eval    | —                                    | ✅ émis depuis adapter       |
| `trigger` stop    | —                                    | ✅ émis                      |
| `token` (onset)   | N/A (pas d'events audio au sens Strudel) | —                      |
| Beat sync         | Aucun natif                          | 🟡 beat/bar globals (idem Hydra) |

Pas d'API transport p5. Kanopi expose `beat`, `bar`, `bpm` via les
hooks `onBeat`/`onBar`/`setBpm` de l'adapter, user code fait
`p.translate(beat * 10, 0)` etc. Même pattern que Hydra. **Attention
au mode instance : exposer via `p`, pas globalThis** — à décider.

Option 1 : exposer `beat/bar/bpm` sur `globalThis` (même pattern Hydra).
Option 2 : exposer sur l'objet `p` passé à la closure sketch.

**Décision recommandée** : option 1 (globalThis). Cohérent avec Hydra,
et dans le sketch user, `beat` reste lisible sans préfixe. Les
collisions globals sont déjà rescue'd.

### D. Library integration — 🟡 à définir

p5 peut charger :
- `loadImage(url)` → PImage
- `loadSound(url)` → SoundFile (avec p5.sound)
- `loadModel(url)` → .obj 3D
- `loadJSON(url)`, `loadStrings(url)`, `loadFont(url)`

Cas **visuels** : extension naturelle de la catégorie `visuals` créée
pour Hydra en phase 2.4 #4. Ajouter un champ optionnel `assetUrl` à
`VisualItem` (déjà anticipé dans `LIBRARY_SPEC.md §2bis`).

Cas **audio** : si v2 on active p5.sound, cross-ref avec audio-banks.
Pas bloquant v1.

### E. Error handling — 🟢 standard JS

p5 laisse les erreurs remonter normalement depuis `setup()` / `draw()`.
Pattern identique à Hydra :

- Parse/JS error → throw → Kanopi flash rouge sur le bloc.
- Runtime error dans draw() → remonte chaque frame (flood potentiel !
  à protéger avec le même `installWarnShadow` pattern que Hydra, cf
  `project_hydra_adapter_quirks`).

**FES (Friendly Error System)** : activé en dev, bloatware en prod
(~300 KB supplémentaires). Désactivable via `p5.disableFriendlyErrors = true`
avant instanciation. **Décision** : désactiver pour v1 (bundle budget)
et laisser Kanopi gérer l'UX d'erreur via son propre Console panel.

### F. Lifecycle — 🟢 bien documenté

| Feature                   | p5 natif                              | Kanopi projeté             |
| ------------------------- | ------------------------------------- | -------------------------- |
| Canvas mount              | `new p5(sketch, container)`           | ✅ `attachP5Canvas(el)`     |
| Re-eval                   | `p.remove()` + `new p5(newSketch, container)` | ✅ identique pattern   |
| Stop / hush               | `p.noLoop()` ou `p.remove()`          | ✅ adapter.stop() → p.remove() |
| Dispose                   | `p.remove()`                          | ✅                          |

Pattern simple : l'adapter garde une référence à l'instance courante,
la détruit + recrée à chaque eval. Pas de double-sketch actif.

## Décision de scope (2026-04-23)

p5.js tombe dans le **cas (a)/(b) hybride** : le runtime est
`@codemirror/lang-javascript` déjà en place (cas a) mais **pas
d'extension CM6 dédiée** pour les globals p5 (cas b). La règle
`feedback_zone_b_scope_rule` s'applique :

- **Dans la phase 2.5 p5.js** : gaps #1-5. Zones A/C/D/E/F. Autocomplete
  globals p5 au backlog.
- **Parkés dans `PROGRESS.md §5.4`** : gaps #6 (autocomplete,
  tooltips signatures), potentiellement hide-code shortcut.

Mode **instance** retenu pour éviter les collisions globals (précédent
Strudel↔Hydra). User écrit `p.ellipse(50, 50, 20)` au lieu de
`ellipse(50, 50, 20)`. À documenter dans le premier snippet Library.

## Block extraction (ADAPTER_SPEC §5.3)

- **Méthode** : **whole-file**.
- **Motif / nœuds** : aucun — un sketch p5 est une unité cohérente
  (`setup()` + `draw()` + helpers partagent le même scope). Ctrl+Enter
  n'importe où évalue tout le fichier.
- **Limites** : impossible d'évaluer "juste la fonction `draw`". C'est
  par design — p5 ne supporte pas d'eval partiel sans risque d'état
  incohérent.
- **Critère de migration AST** : aucun. Les blocs n'ont pas de
  sémantique dans p5.
